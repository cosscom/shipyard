An `env` value in [`.berth/config.json`](/guides/project-config), a
[kit](/guides/kits) or a box's own config can name a secret instead of
holding it, so the file, or the kit, can be shared, even publicly, without
one in it:

```json title=".berth/config.json"
{
  "env": {
    "DATABASE_PASSWORD": "op://dev/shop-db/password",
    "PAYMENTS_SECRET_KEY": "op://dev/Payments test/secret key",
    "OPENAI_API_KEY": "env://OPENAI_API_KEY"
  }
}
```

## References

- `op://vault/item/field` (or `op://vault/item/section/field`, with
  `?attribute=otp` and the like) is 1Password's own reference syntax, read
  with the 1Password CLI on the box: `op read`.
- `env://NAME` passes on a variable from berthd's own environment, under
  whatever name the project wants.
- `box://NAME` is a secret saved on the box through a
  [secret card](#when-an-agent-asks-for-a-secret).
- `gcp://projects/PROJECT/secrets/NAME` (optionally `/versions/N`) is one
  saved in [Google Cloud Secret Manager](#gcp-secret-manager), read with the
  box's own gcloud.

## Setting up 1Password on a box

1. Install `op` on the box. berthd finds it on its `PATH`, in
   `~/.local/bin`, `/opt/homebrew/bin` or `/usr/local/bin`, or wherever
   `$BERTH_OP` says.
2. Sign it in. With a
   [service account](https://developer.1password.com/docs/service-accounts/),
   set `OP_SERVICE_ACCOUNT_TOKEN` in berthd's own environment or in the box's
   `~/.berth/env.json` (which every worktree also gets, so berthd's
   environment is the tighter place). Otherwise run `berthd secret signin`
   on the box (a [team setup](/guides/team-setup#1password-on-the-box) runs
   it as a step): it runs `op signin` there and keeps op's session in
   `box/op-session` in the state directory (`~/.config/berth` on Linux), readable by you alone, for berthd's reads.
   `op signin` on its own only signs in the shell it runs in. op ends a
   session after 30 minutes unused; a service account never ends.
3. Check a reference:

```sh
berth secret test devl op://dev/shop-db/password   # Resolved op://dev/shop-db/password: 24 characters
```

Or from the app: Project settings → Environment → **Test**. Either way the
box reports only whether it could read it and how long the value is.

## How values are handled

The box reads a reference when it builds a worktree's environment for a
hook, a flow, a setup script or `exec`, and keeps the value in memory for
five minutes. It never puts a value in a log, an event, the API or an
error, and writes one to disk only into the store you saved it to (see
[where saved secrets are kept](#where-saved-secrets-are-kept)): config,
`GET /v1/locations/{name}/config` and `GET /v1/env` show the reference. A
value is not expanded, so a `$` in a password stays a `$`.

Terminals, agents and services don't get values from berthd at all: tmux
takes a session's environment as command-line arguments, which other
processes can read, and a service's unit file is on disk and restarted by
the service manager without berthd. So they get the references, and their
program runs behind `berthd secret exec`, which resolves them in its own
memory and then replaces itself with the shell or agent. It prints which
variables it could not set, and reports to the box which resolved and which
failed (never a value), so the box can announce failures. For a service,
`env://` reads the service manager's environment. Each start reads `op`
afresh, so a service that keeps crashing reads it on every restart.

## When a reference fails

berthd runs op without a terminal, so op never asks anything (it used to
sit at "add an account? [Y/n]" in a service's terminal). Not signed in, a
read fails at once with "1Password isn't signed in on devbox: sign in from
Team setup or run `berthd secret signin` on the box".

If a reference cannot be read (no `op`, not signed in, no such item, a read
that takes over 15 seconds), what needs it still starts, without that
variable, and the box sends a `secret.failed` event with the variable, the
reference and the reason, which the app shows as a notification (the same
failure is announced again at most every 10 minutes). A failure
is remembered for 30 seconds, so a broken reference does not run `op` for
every hook. When it reads again, the box sends `secret.resolved`.

A kit that uses `op://` should list `{ "tool": "op" }` in `requires`.

## When an agent asks for a secret

An agent that needs a key or a token can ask you for it instead of having
it pasted into the chat, where it would sit in the transcript, the agent's
context and the host's log:

```sh
berthd secret request ACME_TOKEN --reason "Deploy the acme app to staging"
```

Or with the `berth_secret_request` tool, which takes the same fields. Either
way it returns at once with a request ID (`--wait 90s` waits at most 90
seconds), and the session shows as needing you wherever a question shows:
its chat, its card on the dashboard and a notification. The card has a
masked field with a reveal toggle, the name, the agent's reason as it wrote
it, the session, where the value will be saved and for how long, and
**Save securely** or **Decline**. It also says plainly: the agent can use
this in commands, and a command that prints it puts it in the chat.

**Save securely** sends the value from the app to the box in one direct
call over the paired, pinned connection. It is never in the transcript, an
event, a log, a hook's data or the laptop's offline queue; if the box can't
be reached, the card says so and the value stays in the field. The agent
hears back with a `<berth-notification>` holding a reference such as
`box://ACME_TOKEN`, never the value. A request nobody answers ends after an
hour, and the agent hears that too.

| Option | |
|---|---|
| `--reason WHY` | Shown on the card as written. Required |
| `--new` | Ask for a new value even when one is saved: the card says **Replace** and when the old one was saved. Without it, a saved, unexpired secret's reference comes back at once, with no card |
| `--store local\|gcp` | Where to save it. Default: the project's choice, else the box's, set in Settings → Secrets |
| `--environment staging\|production` | Production shows the environment, the GCP project and any grant in a warning colour, and never expires |
| `--grant SA_EMAIL` | GCP only: give that service account read access to this one secret, shown on the card first |
| `--ttl 1h\|24h\|7d` | Preselect a lifetime. Saved secrets are kept until deleted unless you pick one on the card |

Names are environment-variable style (`ACME_TOKEN`). Saved secrets are
box-wide: any agent on the box can use any secret saved there.

### Using a saved secret

A saved secret is handed out only on demand, never through a session's
environment:

```sh
# The value in a variable, for one command:
berthd secret exec --env ACME_TOKEN=box://ACME_TOKEN -- ./deploy.sh

# For a CLI that wants a token file: a private temporary file (in
# $XDG_RUNTIME_DIR or /dev/shm when the box has one), its path in the
# variable, removed when the command ends, signals included:
berthd secret exec --file GOOGLE_APPLICATION_CREDENTIALS=box://ACME_SA_KEY -- gcloud …
```

A reference that can't be read stops the command with why. `box://` and
`gcp://` also work wherever `op://` does: a project's `env`, the box's
`env.json` and `berth secret test`. There is no command that prints a value.

### Where saved secrets are kept

The **Local** store, the default, keeps them on the box:

- **macOS:** the login Keychain, written through `security` with the value
  on its standard input, never in its arguments.
- **Linux** with a Secret Service on the session bus (GNOME Keyring,
  KeePassXC): there, through libsecret's `secret-tool`, the value on its
  standard input.
- **Otherwise:** an encrypted file, `box/secrets/values.json` in the state
  directory, each value sealed with XChaCha20-Poly1305 under a key in its
  own file, `box/secret.key`, readable by you alone. This guards against a
  leaked folder, a backup or a grep. It does not guard against another
  program running as the same user, which can read the key too.

Beside them the box keeps what it saved (name, store, environment, who
asked and why, when it expires; never a value) in `box/secrets/index.json`,
and deletes expired secrets every minute. Settings → Secrets lists them per
box, with **Delete**; a production secret needs its name typed first.

To remove saved secrets by hand (say after going back to a build without
secret cards): delete them in Settings → Secrets first, or remove the
Keychain items whose service is `dev.berth.secrets`, run
`secret-tool clear service dev.berth.secrets name NAME`, or delete
`box/secrets/` and `box/secret.key`.

### GCP Secret Manager

Set GCP as the box's store, or one project's, in Settings → Secrets, with a
GCP project. berthd reads and writes with whatever gcloud is signed in as
on the box, and **never changes a project's IAM**. A missing permission
fails on the card, naming it. The least it needs, as a custom role:

- `secretmanager.secrets.create`, `secretmanager.secrets.get`,
  `secretmanager.secrets.list`
- `secretmanager.versions.add`, `secretmanager.versions.access`
- `secretmanager.secrets.delete`, to delete from Settings
- `secretmanager.secrets.setIamPolicy`, only for `--grant`

On **Save securely** the box creates a secret with ID `NAME` and the labels
`shipyard=true`, `shipyard-environment`, `shipyard-location` and
`shipyard-box`, then adds the value as a version. It refuses to add a
version to a secret by that name without the `shipyard` label: one it
didn't make is left alone. A labelled one gets a new version, which is how
`--new` rotates it. `--grant` adds `roles/secretmanager.secretAccessor` for
that service account on that one secret only; mounting it on a service
(`gcloud run services update --update-secrets …`) stays the agent's own
step. The agent gets `gcp://projects/PROJECT/secrets/NAME`. Settings lists
the secrets labelled `shipyard=true` in each project the box or a project
names.

### Adding a provider

Stores are providers behind one Go interface, `SecretStore` in
`internal/box/secretstore.go`: save, resolve, list and delete, with a label
for the card. A provider is one file that registers itself in an `init`
with `registerSecretStore`: its id (what `--store` names), its reference
scheme, what it can do (expiry, labels, grant), how to validate a
reference, and how to open its store at a place (a GCP project, a Vercel
team). `secretstore_gcp.go` is the example. The card, the API,
`berthd secret exec` and Settings only go through the interface, so a new
provider changes nothing else; `TestAThirdProviderPlugsInFromItsOwnFile`
shows one doing it.
